## 第十七轮：曲库能力后缀 + 手势冲突 + 「应用成功却说没有结果」根因（r40–r45）

- **手动找歌词四个曲库加能力后缀**：chip 文案 = 品牌 + 「 · 」+ 能力（`LRCLIB · 时间轴`、`网易 · 译文`、`QQ · 译文`、`酷狗 · 时间轴`），下面一行 `hint_*` 说明所选曲库到底带什么（酷狗只有原文时间轴，写明「当作最后的备选」）。品牌用简称（网易/QQ/酷狗），网络体检行仍用全称（`network.ep_*`）。
- **手势冲突**：chip 行原来是 `HorizontalScrollView`，横向拖动既要滚动它又要切 tab，一滑就跳「同步」页。改成**两行两列**（LRCLIB+网易 / QQ+酷狗），不再需要横滑；同时在 `pointHitsEditable` 里把 `HorizontalScrollView` 也算作「该点属于子控件」，今后任何横滑区域都不会被当 tab 手势。
- **⚠️ 关键踩坑（用户报「明明有结果，却说没有 xx 的结果」）**：`AppI18n.addCatalogueNameStrings` 是「keys 数组 + 每语言一行」的写法，我在行里插了 `loaded_format` 的值、却没同步插 keys 里的键，导致**后续所有字符串整体错位一格**——`no_results_format` 拿到了「已应用 %s 的歌词」这类值，表现就是应用成功却显示「没有结果」。已把 keys 顺序改回与行一致，并在 `tests/check_module_boundaries.py` 增加 **键数 == 行宽-1** 的断言（现 52 项），防止再犯。
- **文案去 LRCLIB 化**：搜索中 / 加载所选 / 失败 / 结果为空 / 应用成功，全部带曲库名（`searching_format`、`selecting_format`、`failed_format`、`no_results_format`、`loaded_format`、`result_empty_format`）。取词成功但曲库没给词时，改说「这条结果在 X 那边没有歌词，换一条试试」，不再谎称「没有搜索结果」。
- **探针结论**：网易云 search→lyric 链路正常；**酷狗 `krcs.kugou.com/search?hash=` 对很多歌直接返回 `candidates: []`**（实测 Supper's Ready Live），所以酷狗「有搜索结果但取不到词」是上游行为，不是我们的 bug。
- **选中态被冲掉**：`applyPanelControlPalette` 会给所有可点 TextView 重刷背景，chip 的白色药丸因此消失；在 `buildLyricsMetaMenuPanel` 末尾（调色板之后）重新 `setSelectableButtonState`。
- 另外：网络区预设切换 toast 的「已切换：」中文硬编码改用 `network.switched`；`NetworkRegion.Endpoint.label` → `labelKey`（9 个品牌键）。
- **已知遗留**：`tests/run_settings_ui_regression.py` 在 r39 基线就失败（`check 1284`，`lyricsRegenerateButton.enabled` 状态机），与本次改动无关，待单独排查。
